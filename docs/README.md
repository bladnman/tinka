# Operating a Tinka instance

Start with the [root README](../README.md) for installation and agent setup. Node >=22 is required. No build or dependency installation is needed.

For a portable project, commit `TINKA.md`, the `AGENTS.md` pointer, `tinka/project.json`, `tinka/setup.mjs`, `tinka/.gitignore`, and the complete boards, including disk notes. Use the visible `tinka/` folder for setup and `design/boards/` for design content by default. `node tinka/setup.mjs` restores the pinned app in `tinka/app` and recreates `tinka/local/config.json` with this checkout's absolute paths. It does not start a stopped app. Start with the command in `TINKA.md`. App and local state are ignored by the generated tooling ignore file; review broader project ignore rules before committing. No installed skill or registry is needed. The app's [agent guide](AGENT.md) and [protocol](PROTOCOL.md) are the version-specific authority; board instructions travel with the board.

The external config has `schemaVersion: 1`, an absolute `boardsRoot`, `projectLabel`, `port`, and `portMode` (`auto` or `fixed`). The CLI defaults to automatic ports and the current folder's name. Legacy configs without `portMode` remain fixed. The legacy `title` field is accepted for compatibility but does not replace Tinka's brand or project label.

The server never reads a global registry. A project's config defines its entire workspace. Its adjacent `.pid.json` records the owned process, actual port/URL, and installed version; `.log` receives managed output. The PID claim is acquired before binding so concurrent starts of one config cannot choose different ports. A dead PID record can be reclaimed; a live or unrecognized owner is never killed. A stale `.pid.json.recovery` directory indicates an interrupted reclaim; verify no startup is in progress before removing that directory and retrying.

`start` returns after the owned process reports ready. `stop` validates the exact CLI/config/token in the process command. Foreground `serve` processes use Ctrl-C; they cannot be stopped through an unverified managed record. If stopping fails, inspect the matching log and PID record rather than signaling by port.

A new automatic instance begins at 43821, with 100-port increments and 20 attempts. The selected port is saved only after binding. Restart tries the saved port first and may advance if occupied. A fixed collision is an error. No process probes, adopts, or signals a different project's server. `/api/config` and `/api/health` expose the current label, workspace identity, version, and URL to the loopback client.

Before explicit migration, each immediate folder with `board.json` is discovered automatically. Schema 2 workspace metadata defaults to `boardsRoot/.tinka` (or absolute config `workspaceRoot`). Keep that directory with the project. A custom absolute workspaceRoot is machine-specific and requires deliberate backup/restoration; setup does not port or relocate arbitrary paths. Schema 2 notes/stars/status are canonical item data; placement layout and local archive state belong to boards. Migrated legacy folders remain unchanged resource payloads and are not listed a second time. See [PROTOCOL.md](PROTOCOL.md) for experiments and build states. Legacy notes live in each board's `.state/notes.json`; canonical graph notes live in item metadata. Browser caches are namespaced to the canonical config and boards paths. Moving either path creates a new browser namespace but does not alter disk notes. Old unscoped browser notes are not automatically merged; export browser-only notes from the old app before upgrading.

Use one installed app copy per project for independent upgrades. The installer uses the old CLI to stop only that installation's matching managed process, replaces the complete app directory, then restarts it through the new CLI if it was running. Stopped installations stay stopped. It retains an adjacent backup; a failed swap/restart restores that backup and attempts to restart it. Configuration and boards are never included in an app replacement. The install receipt records the chosen version and checksum. Keep the backup until the update is accepted.


## Workspace operation and recovery

`workspace migrate --dry-run` is the default and changes no data. Review its report, back up the external boards/resource folders and workspace metadata, then use `--apply` explicitly. `workspace init --apply` uses the same path for an empty workspace. Repeat migration safely; existing graph IDs and review data are preserved. Original manifests, raw feedback, build history and files remain in their legacy folders, while migration metadata records lineage.

Use `workspace show` to inspect durable state and `workspace op --file operation.json` for edits. CLI and HTTP use the same transaction lock and revision checks. An interrupted transaction is rolled forward when the store is next opened with valid lock ownership. Recorded owners are reclaimed only when provably dead; missing/unverifiable ownership or an orphan recovery guard returns 409. Before manually recovering, stop and verify all workspace writers, inspect and archive/rename only the orphan lock/guard metadata, and preserve the workspace plus pending.json for redo. No timeout forcibly breaks an unknown lock, and no universal power-loss recovery is promised. Stop only this instance before restoring a complete known-good metadata backup. For a return to the untouched legacy view, move the workspace metadata directory to a recoverable archive outside the active workspaceRoot; do not delete original board/resource folders. Schema 2-only edits require restoring the metadata archive to reappear. Keep backups until accepted.

The config's `workspaceId` is derived from machine-local config and boards paths, adding a custom metadata root when it differs from the default, and protects writes. `/api/workspace.workspaceId` is the durable graph identity and can survive checkout relocation. Send the config identity in `x-tinka-workspace`, never the graph identity. All writes require JSON, a matching live identity and same-origin loopback request. Changing the config's roots while the server is running disables writes until the instance is restarted with that config.
